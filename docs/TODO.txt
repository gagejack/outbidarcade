IMPORTANT CONSTRAINT
====================

RUN ONE UVICORN WORKER. Do not add --workers.

Two pieces of state live in process memory:
  - the rate limiter (_HITS in main.py)
  - the board cache (_board_cache in db.py)

With N workers each process gets its own copy. Rate limits would multiply
by N (a 10-per-15-min login limit becomes 10*N), and board caches would
diverge after a write, so some visitors would see a stale board.

Adding workers is also not the speedup it looks like: every route is
sync def, so FastAPI already serves them from a threadpool. The real
ceiling is SQLite, and more processes contending for one file makes that
worse, not better.

If more capacity is genuinely needed, the order is:
  1. Move _HITS and the board cache to shared storage (or Postgres)
  2. Only then add workers

COMMON COMMANDS
===============

Redeploy after a git push:
  cd ~/outbidarcade
  git pull
  docker build -t outbid-arcade .
  docker stop outbid-arcade
  docker rm outbid-arcade
  docker run -d --name outbid-arcade -p 8080:8080 \
    -v ~/outbid-data:/data --restart unless-stopped outbid-arcade

Check things:
  docker ps
  curl -s -o /dev/null -w "%{http_code}\n" http://localhost:8080
  curl -s http://localhost:8080/api/board
  sudo systemctl status cloudflared     # q to exit the pager

Logs:
  docker logs outbid-arcade --tail 50
  sudo journalctl -u cloudflared -n 50 --no-pager
